# Parser and pipeline internals

**TMDL parser (`tmdl_parser.py`)**
- Core structure parsing goes through `_parse_tree()`, which builds a tree of `TmdlNode` from indentation. Nested TMDL structure is parsed only this way; regex is used solely to locate block boundaries.
- `_extract_blocks()` is a block-boundary locator only (finds where a `column`/`measure`/`calculationItem` block starts and ends by indentation). It does not parse the block's internal structure.
- `_classify_m_content()` classifies M (comments stripped) with a fixed precedence; the first rule that fires wins, and every result records `classification_reason`:

  | # | Rule | `source_type` |
  |---|---|---|
  | 1 | `PBI_ResultType` is `Text`, `Number`, `Date`, `DateTime` or `Boolean` | `scalar_helper` |
  | 2 | `#table(` or `Table.FromRows(` present | `hardcoded` / `embedded` |
  | 3 | any `Namespace.Function(` call in the whole block outside the M standard library (`_STDLIB_NAMESPACES`) and `_TRANSFORM_FNS`; the first such call in source order is the connector | `connector` |
  | 4 | `Table.Combine({...})` / `Table.Append({...})` whose items resolve to queries: `#"name"`, a bare name, or a step of the same block assigned `#"name"`; other local steps are dropped | `table_combine` |
  | 5 | the first step references a query: `Source = #"x"`, `Source = X`, or a first `let` binding `a = #"x"` / `a = X` | `derived` (quoted) / `derived_table` (bare) |
  | 6 | no query reference, and the block builds a table from scratch | `generated` |
  | 7 | none of the above | `unknown` |

  `builds_table` is set on every result when the block calls a scratch builder (`List.Generate`, `List.Dates`, `List.DateTimes`, `List.Numbers`, `Table.FromList`, `Table.FromRecords`, `Table.FromColumns`). Real queries use these as transformations too, so a query reference in rule 5 always wins over them.

  Function versus table is decided before this, in `_classify_expression()`: `PBI_ResultType = Function` or a body that starts with a function signature (optionally typed, `(x as text) as table =>`) is `function_def`.
- Adding a new connector with custom detail extraction: add a branch to `_extract_connector_details()` in `tmdl_parser.py`, add an entry to `CONNECTOR_TYPE_LABEL` in `source_resolver.py`. That dict is the only source of connector labels - `readme_generator.py` imports it, so there is no second copy to keep in sync. Generic connectors with no custom branch still get classified and labeled - the custom branch is only needed to extract extra detail fields (server, database, url, etc.).
- `_SOURCE_TYPE_LABEL` in `readme_generator.py` is a separate axis: it names non-connector source types (`hardcoded`, `embedded`, `table_combine`, `dynamic`, `unresolved`, `function_def`, `scalar_helper`, `generated`). Extend it only when a new `source_type` value is introduced.
- M comment stripping (`_strip_m_comments`) must run before any connector detection.

**Source resolver (`source_resolver.py`)**
- Three-tier resolution: terminal connectors (tier 1) → derived/custom_function chains (tier 2) → inline table sources (tier 3).
- Terminal types listed in `_TERMINAL_TYPES` (including `table_combine` and `generated`) - chain walking stops there.
- A `derived` expression or table whose parent is an M parameter or a `scalar_helper` is not copied from that parent: it resolves as `generated` when its `builds_table` is true (a calendar seeded from a start date), otherwise as unresolved with the reason `first step references parameter '<name>'` or `first step references scalar helper '<name>'`. An `unknown` expression reports its `classification_reason` as the unresolved reason.
- `resolve_sources()` does multiple passes to handle chains where derived expressions reference other derived expressions.
- Shared expressions or inline M that reference a loaded table resolve from the
  model's own tables: tables whose partition is a `source_ref` pointer act as
  aliases to that expression, and derived expressions that reference tables are
  resolved in the same multi-pass loop as inline table sources.

**Generator (`readme_generator.py`)**
- `_SECTIONS` is the single ordered list of `(key, title)` for both renderers. `generate_readme` and `generate_html` take every section heading from it and render the sections in its order; the `unresolved` section is emitted only when there is an unresolved source, with a warning glyph in front (`⚠` in Markdown, `&#9888;` in HTML).
- Table of contents: `_rendered_sections(resolved)` is `_SECTIONS` minus `unresolved` when nothing is unresolved, and it drives both the contents block and the section loop, so the two cannot disagree. Every section has an anchor id from its key (`_section_anchor`: `_` becomes `-`, for example `data-sources`). Markdown puts a bold **Contents** list after the title and an explicit `<a id="..."></a>` line before each `##` heading, because auto-generated heading slugs differ between renderers (GitHub, Azure DevOps) and break on the warning glyph; HTML puts a `<nav class="toc">` after the subtitle and the same id on each `<h2>`. The contents label is not a heading, so the `##` / `<h2>` headings stay exactly the `_SECTIONS` titles. The plain-text and JSON writers have no table of contents.
- Lineage (`include_lineage`, Markdown only, off by default): `_lineage_graph` builds nodes and edges from the resolver output for the Data Sources tables (loaded, including hidden, and not loaded; support and auto-date tables excluded). Each table's path is its `source_ref` (if any) followed by `ResolvedSource.chain`, ending in a cylinder node for a connector (identity: connector label plus the first of server and database, URL, entity, SharePoint URL, file, DSN), the combine's input queries (each followed to its own source), or a per-table end node for generated, hardcoded, embedded, dynamic or unresolved (dashed). Scalar helpers and functions are never drawn. `_lineage_section` renders a `### Lineage` sub-section at the end of "1. Data Sources" as a Mermaid `flowchart LR`; node ids are `n` plus the first 10 hex digits of SHA-256 over the node identity (`table:<name>`, `query:<name>`, `source:<label>|<detail>`, `end:<type>:<name>`), never Python's `hash()`, so they are independent of input order and `PYTHONHASHSEED`. Node and edge lines are sorted; labels escape `&`, `"`, `<`, `>` as Mermaid entity codes. HTML, text and JSON ignore the option, and `Pipeline.run` logs one warning when it is set for another format.
- Every table is built once by a row builder (`_overview_rows`, `_source_rows`, `_support_rows`, `_column_rows`, `_table_measure_rows`, `_calc_item_rows`, `_format_groups` / `_format_rows`, `_folder_measure_rows`, `_function_rows`, `_relationship_rows`, `_role_rows`, `_parameter_rows`, `_unresolved_rows`, `_statistics_rows`) and rendered by `_md_table_rows` or `_html_rows`. Cells are plain text or the small cell types `_Code` (a name as code, optional plain suffix), `_CodeList` (names as code, `-` when empty) and `_CodeRefs` (`name (table)` pairs, `-` when empty). Shared filters: `_visible_relationships` (drops auto-date relationships) and `_support_split`. A new table goes into a row builder first, then into both renderers.
- Markdown doubles backslashes in measure folder headings (`_measures_section`); HTML and text print the same folder name literally. That is Markdown escaping, not a content difference between the renderers.
- `generate_text` is the plain-text writer (`--format txt`). It is built only on `_SECTIONS` and the row builders, rendered through `_text_cell` / `_text_table` (columns padded to the widest cell, two spaces apart, header underlined with `-`, every line right-stripped). Headings are underlined with `=` (title), `-` (sections, the unresolved one prefixed with `! `) and `~` (sub-headings); DAX is indented by four spaces; `⚠` becomes `!`. Content follows the Markdown renderer, so there is no third set of choices. The pipeline writes `.txt` with LF line endings on every platform.

**JSON writer (`json_writer.py`)**
- `generate_json` builds the document from the parsed `SemanticModel` and the resolver output, never from rendered text or the row builders. It reuses only model-level helpers from `readme_generator.py`: `_collect` (the table split that gives `kind`), `_visible_relationships`, the function and parameter usage maps, and the hidden-reference finder.
- Layout and enums are published in `docs/tmdl-lens-output.schema.json`, versioned by `schema_version`. A layout change bumps it and updates the schema in the same commit; `tests/test_json_writer.py` pins the writer's enum constants against the schema.
- Determinism: every list of named items is sorted by name (relationships by their four endpoints, warnings by code, table, object and detail, physical tables by schema and table); `source.chain` keeps its lineage order because it is a path. No timestamp, no tool version, `ensure_ascii=False`, two-space indent, trailing newline; the pipeline writes `.json` with LF line endings. Tests pin input-order independence and identical bytes across `PYTHONHASHSEED` values.
- Typed values: `kind` from the `_collect` split; `source.type` is the resolver's terminal type; `cardinality` maps the parser's four display strings (anything else is `null`); `cross_filter` and `security_filter` map the TMDL values case-insensitively. A gap is explicit: `{"resolved": false, "reason": <resolver reason>}`; `source: null` means the table has no M source. `combine_sources` is looked up from the terminal expression's own `SourceExpression`, because `ResolvedSource` does not carry it.
- Warnings: `unresolved_source` for every unresolved entry, `hidden_reference` for every hidden object referenced by a measure or calculated column, computed regardless of `include_dax`.

**Report parser (`report_parser.py`, report-layer usage stage A)**
- `parse_report_layer(report_dir)` reads `<name>.Report/definition/` of the PBIR format: `report.json`, `pages/pages.json`, `pages/<page>/page.json` and `pages/<page>/visuals/<visual>/visual.json`. It is read-only, independent of `tmdl_parser.py`, and not imported by the pipeline, the CLI, the GUI or any writer yet, so it changes no output.
- Result: `ReportLayer(pages, filters, problems)`; `Page(name, display_name, is_hidden, filters, visuals)`; `Visual(name, visual_type, is_group, parent_group, is_hidden, usages)`; `FieldUsage(field, usage, role)` with `FieldRef(table, name, kind, hierarchy)`, `kind` one of `column`, `measure`, `hierarchy_level`.
- Every model-field reference in a document is recorded: `Column`, `Measure`, `Aggregation` (unwrapped to its column) and `HierarchyLevel`; a `PropertyVariationSource` (auto date hierarchy) maps to its column. `SourceRef.Entity` names the table directly; `SourceRef.Source` is resolved through the nearest enclosing `From` alias list. `Literal`, `ResourcePackageItem` and `SelectRef` are not model fields and are ignored, including an `Aggregation` over a `SelectRef` (a visual calculation).
- `usage` comes from the first marker on the JSON path: `queryState` gives `projection` with the query role (`Values`, `Category`, ...), `sortDefinition` gives `sort`, `filterConfig` gives `filter`, `objects` / `visualContainerObjects` give `formatting`, anything else `other` (for example a drillthrough `pageBinding`). `Page.filters` and `ReportLayer.filters` hold all page-level and report-level references with their tags.
- Determinism: pages in `pages.json` `pageOrder`, then by name; visuals by name; usages de-duplicated and sorted by table, name, kind, hierarchy, usage, role. Never raises for content: an unreadable or non-object file, an unresolvable reference, a missing definition or a PBIR-Legacy `report.json` becomes a line in `problems`.
- Fixture: `tests/fixtures/report/Example.Report/` (invented names), exercised by `tests/test_report_parser.py`.

**Pipeline (`pipeline.py`)**
- Pure-Python orchestration with no GUI/thread dependencies: finds `.pbip` files, runs parse → resolve → generate per report, returns `SingleResult`/`PipelineResult`.
- `_locate_model()` finds the model folder with a fixed precedence: the first `report` entry in the `.pbip` `artifacts`, then that report folder's `definition.pbir` `datasetReference`, then the `<pbip name>.SemanticModel` guess. `byPath` (relative, `/` separators) must point to an existing folder, otherwise the report is skipped with `definition.pbir points to a missing folder: <path>`; `byConnection` is skipped with `report uses a live connection (byConnection), no local semantic model`. The guess is used only when the `.pbip` or `definition.pbir` cannot be read or holds no reference (an empty `.pbip`, or no report folder). `_model_problem()` then requires `definition/`; a folder with `model.bim` or with neither is skipped. All these skips happen in `run_single` before the hash and before any output file is opened, are logged at `warn`, and produce no hash entry. When the model folder differs from the guess, `run_single` logs it once (`  model: <relative path> (definition.pbir)`). The parser never sees a folder without `definition/`, and `model.bim` is never parsed. The multi-`.pbip` folder guard in `run()` is unchanged.
- `skip_unchanged` computes a SHA256 of each report's `.tmdl` files plus the generator-relevant config (`include_dax`, `include_lineage`, `output_format`, `owner`, `team`, `refresh_schedule`), the report's output path and the tool version; the hash is computed on every run inside the per-report error handling. `run_single` skips with reason `unchanged` when the hash stored for the report's path relative to `reports_folder` (forward slashes) matches and the output file already exists; a missing or differing hash regenerates even when `overwrite` is off. Hashes are stored only after a successful write, keyed by that relative path. The app persists the hashes to `config.json` under `file_hashes`.

**CLI (`cli.py`)**
- argparse-based headless interface over `Pipeline`, no GUI imports. Installed as the `tmdl-lens` console command via `pyproject.toml` `[project.scripts]`.
- Exit codes: 0 success, 1 report failure or missing reports folder, 2 missing `--reports-folder`.
- Reads settings from a `config.json` only when `--config` is passed; that is also the only way `--skip-unchanged` hashes persist between runs (CLI flags override file values). A missing config file logs a warning and is never created; a file that exists but does not parse (invalid JSON, non-object JSON, non-UTF-8) is an error with exit code 2 and is never written; a UTF-8 byte order mark is accepted. Values used for the run go through `config.check_types()`; a wrong-typed value is warned about and falls back to the CLI default, while write-back keeps the raw file content. Relative `reports_folder`/`output_folder` values from the file resolve against the config file's folder. Write-back merges `file_hashes` into the loaded settings and replaces the file atomically. The standard config.json location belongs to the GUI, so the CLI never writes there implicitly.

**Config file - one file**
- `config.json` - program settings (output format, paths, watcher) plus optional documentation metadata (owner, team, refresh schedule) and `skip_unchanged` content hashes (`file_hashes`). `config_path()` resolves three cases: next to the executable when frozen, the repo root when the package's parent folder holds `pyproject.toml` (source checkout), otherwise a per-user folder (`%APPDATA%\tmdl-lens` on Windows, `$XDG_CONFIG_HOME/tmdl-lens` or `~/.config/tmdl-lens` elsewhere). On a pip install with no file there, `load_result()` copies a legacy `config.json` from the package's parent folder once, never raising and never deleting it.
- `config.py` is the only reader and writer for both CLI and GUI: `read_file()` (UTF-8 with an optional byte order mark, JSON object required, returns an error string instead of raising), `check_types()` / `normalize()` (each known key checked against the type of its default; a rejected value is replaced by the default with a warning naming the key, the value found and the value used), `load_result()` returning a `LoadResult` (config, path, error, warnings, migrated_from) and `write_atomic()` (temporary file plus `os.replace`). Defaults are always copied with `copy.deepcopy`.
- The GUI never writes `config.json` implicitly (close, hash persistence, first-launch save) after a failed load; an explicit Save overwrites it and clears the error. Every failed save is logged.
- `config.validate_config()` returns warning strings for an unset `reports_folder`, `watch_debounce` outside 1-300, and invalid `output_format` (accepts `html`, `md`, `txt` or `json`); `app.py` logs them at startup. Path existence is not validated there: the CLI errors on a missing reports folder (exit 1), the GUI checks the folder when a run starts, and the pipeline creates the output folder.

**GUI (`app.py`)**
- CustomTkinter, dark theme only. Colors defined in `COLORS` dict at top of file.
- Single scrollable Configure pane (paths, options, watcher, optional documentation metadata) beside the log panel, action bar, and status bar. The left sidebar's nav buttons are non-functional; there is no top tab bar.
- All pipeline work runs in a background thread (`_run_pipeline_async` → `_on_pipeline_done`). The watcher delegates to `Pipeline.run_single()`. Pipeline work never runs on the main thread.
- Log panel uses native `tk.Text` with color tags - use `self.log(message, level)` for all output. Levels: `ok`, `warn`, `err`, `info`, `msg`.
- Watcher (watchdog) is optional. Guard all watcher code with `WATCHER_AVAILABLE` check.

**Tests**
- Tests are pytest and run from the repo root with `python -m pytest` (dev deps first: `pip install -r requirements-dev.txt`).
- Tests run against the sample report in `sample/`, which is also the published example output. Extend it deliberately when a new case is needed, and keep the existing cases intact.
- Run the suite after changing `tmdl_parser.py`, `source_resolver.py`, `readme_generator.py`, `config.py`, or the tests.
- `tests/test_golden.py` compares the Markdown, HTML, plain-text and JSON output byte for byte (after newline normalisation) with golden files for four cases: `full` (the sample with owner, team, refresh schedule and DAX), `nodax` (the sample without DAX or metadata), `empty` (an empty model) and `edge` (a dataclass-built model in the test module covering display folders with a backslash, a blank parameter value, an auto-date table and a hidden loaded table). The `full` Markdown golden is `sample/README.md` itself; every other golden is in `tests/golden/`, outside the `tools/check_rules.py` sample guard. The same module checks that every renderer emits the section headings in the same order, and that the text output carries no markup or trailing whitespace.
- A generator change that alters output regenerates `sample/README.md` and every file in `tests/golden/` in the same commit: run `python -m pytest tests/test_golden.py` with the environment variable `TMDL_LENS_UPDATE_GOLDEN=1` (in cmd: `set "TMDL_LENS_UPDATE_GOLDEN=1"`). An update run writes the files with LF line endings and reports each golden test as skipped, so it can never pass silently; run the suite again without the variable afterwards and review the golden diff.
